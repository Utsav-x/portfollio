The bidding engine

The piece of my own work I'd most want to be asked about. Built for Rarità, a real-time auction marketplace.

The problem. A hot auction takes many concurrent bids per second. Writing each one to PostgreSQL on the request path makes the database the bottleneck, and doing read-modify-write on a shared price from multiple workers lets two bids interleave into an inconsistent state — two bidders can both "win" at the same price.

The approach. Authoritative auction state — current price, highest bidder, bid count — lives in a Redis hash rather than the database. Every bid goes through a single atomic Lua script that validates and accepts it inside Redis, so the check and the write cannot be split by another bid. The script only accepts a bid that strictly raises the current price, which makes the most recently accepted bid the winner by definition.

Money. Lua numbers are doubles, so currency is held as integer paise. Every amount the platform handles stays well inside 253, and the arithmetic is exact.

Getting it into Postgres without losing anything. Accepted bids append to a per-listing Redis buffer, and a periodic Celery task drains them to PostgreSQL in batches. Each bid carries a monotonic per-listing sequence number, and the state hash tracks how far persistence has got. Re-draining the same buffer is therefore a no-op — so a crash between the database commit and the buffer trim can never double-insert. Every auction-close path force-drains the buffer before deciding a winner, reading the per-listing buffer directly rather than trusting the dirty set, so a close is never at the mercy of the periodic drain's timing.

The escape hatch. The whole engine sits behind a feature flag. Turn it off and every caller falls back to the original synchronous database path. A performance optimization that cannot be switched off is a liability.

Catalogue ETL & entity resolution

Python · PostgreSQL · Celery Beat

A CSV-to-database importer with a category-agnostic schema: core columns map to first-class fields, everything else folds into a JSON attributes column, so a new source format loads without a migration. Identity is a hashed dedup key derived from normalized columns, so the bulk importer and the incremental monthly fetcher agree on what counts as the same record and re-running a load is idempotent. Matching is exact-key first, then a PostgreSQL trigram similarity fallback bucketed by brand, scale and packaging — so variant spellings of one item resolve to a single row.

Two-stage AI vision & valuation

Python · Gemini · OpenAI · Claude · PostgreSQL

Stage 1 extracts a structured catalogue card from user photos with no pricing involved; Stage 2 runs a separate web-search-grounded valuation against sold comparables. Splitting them stopped price speculation leaking backwards into identification. The provider is chosen by configuration behind one interface, so the model vendor is a setting rather than a rewrite. Output is schema-constrained JSON with parsing, sanitization, price validation and retry with backoff, so malformed or hallucinated output fails closed instead of reaching the database. A valuation cache keyed on item identity means two users scanning the same item share one expensive grounded call.

Time-decayed trending

Redis · Django · PostgreSQL

Lifetime view counters mean a listing that collected views over three weeks always beats one that collected the same number yesterday. This keeps rolling counters in one Redis hash per hour rather than per listing, so recomputing the whole site costs a fixed number of reads no matter how large the catalogue grows. Every entry point swallows its own exceptions: a Redis outage degrades the ranking to "no recent data" and falls back to lifetime rates, and can never break the request that was recording the view.

Index options time-series analysis

Analysis over minute-bar Nifty and Sensex data spanning 2018–2025 — roughly 1,800 trading days of intraday series — developing and evaluating a strike-bucket options strategy. Ingests the instrument master via API, filters and types it, and merges it against a constructed strike/expiry frame to resolve tradeable instruments. Indicator state carries forward through a cache between runs so signals stay consistent across restarts.
